FIX THE REJECTED SPONSORSHIP PAYMENT LIFECYCLE — PRODUCTION-SAFE

The latest audit rejected the implementation because there is a race condition between:

1. sweepExpiredSponsorships()
2. PayPal/test-provider payment finalization
3. sponsorship activation

DO NOT redesign the sponsorship system. Fix the lifecycle race using the existing architecture and preserve all existing functionality.

==================================================
CRITICAL BUG
==================================================

Current behavior:

- A sponsorship starts as pending.
- It has a 15-minute local reservation TTL.
- sweepExpiredSponsorships() finds stale pending sponsorships.
- The sweep uses an advisory lock.
- Payment finalization does NOT use the same advisory lock.
- Therefore this race is possible:

T1:
Sweep selects stale pending sponsorship.

T2:
Payment provider capture succeeds.

T3:
Payment finalization activates sponsorship and commits.

T4:
Sweep performs its unconditional UPDATE by sponsorship ID.

T5:
The now-active sponsorship gets changed to cancelled.

Result:
Payment = succeeded
Invoice = generated
Sponsorship slot = cancelled

THIS MUST NEVER BE POSSIBLE.

==================================================
GOAL
==================================================

Make sponsorship state transitions atomic and serialized.

A successfully verified provider payment must NEVER be followed by the expiration sweep cancelling the purchased sponsorship.

The expiration sweep must NEVER overwrite an already-active sponsorship.

==================================================
REQUIRED FIX #1 — SHARED ADVISORY LOCK
==================================================

Use the SAME sponsorship-specific advisory lock mechanism for BOTH:

A. sweepExpiredSponsorships()
B. payment finalization / sponsorship activation

Payment finalization must acquire the sponsorship advisory lock BEFORE:

- reading sponsorship state
- validating payment state
- activating sponsorship
- changing sponsorship lifecycle state
- writing the final payment state
- creating/updating invoice state where relevant

The sweep must continue to use that same lock.

The lock must be held through the complete transaction/state transition.

Do NOT merely add a lock around a SELECT while leaving the UPDATE outside the protected transaction.

==================================================
REQUIRED FIX #2 — DEFENSIVE CONDITIONAL UPDATE
==================================================

Even with the advisory lock, make the expiration update defensive.

Never do:

UPDATE sponsorships
SET status = 'cancelled'
WHERE id = $id;

Instead, only cancel if the sponsorship is STILL stale and pending.

Conceptually:

UPDATE sponsorships
SET status = 'cancelled', ...
WHERE id = $id
  AND status = 'pending'
  AND expires_at <= now();

Use the actual schema/status names already present in the project.

The sweep must verify the affected row count.

If zero rows were updated, treat the sponsorship as no longer eligible for expiration and do not overwrite anything.

An ACTIVE sponsorship must be impossible to change to CANCELLED through the expiration sweep.

==================================================
REQUIRED FIX #3 — PAYPAL TTL PROBLEM
==================================================

The current fixed 15-minute local reservation creates another lifecycle problem.

A legitimate PayPal approval/capture can take longer than the local 15-minute TTL.

The system must NOT interpret:

"local reservation expired"

as automatically meaning:

"the PayPal payment/order is invalid."

Do NOT release a valid provider-created/approved PayPal order solely because the local 15-minute TTL elapsed.

Before freeing the sponsorship capacity for a PayPal sponsorship that has an associated provider order:

- determine the current provider/payment state when appropriate
- distinguish between:
  - never approved / abandoned
  - approved
  - captured/succeeded
  - pending
  - failed
  - cancelled
  - unknown/reconciliation-required

If PayPal has already created/approved a valid order, do not blindly cancel the sponsorship solely because 15 minutes passed.

If the provider state cannot safely be determined, preserve the record for reconciliation rather than creating a false cancellation.

Use the existing PayPal integration and provider verification mechanisms. Do not invent a second payment system.

==================================================
REQUIRED FIX #4 — PAYMENT FINALIZATION RULE
==================================================

When PayPal capture is verified as successful:

1. Acquire the sponsorship advisory lock.
2. Begin the appropriate database transaction.
3. Re-read the sponsorship FOR UPDATE where appropriate.
4. Re-read the payment/order state.
5. Verify that this payment actually belongs to this sponsorship.
6. If sponsorship is pending:
   - activate it.
7. If sponsorship is already active:
   - make the operation idempotent.
8. If sponsorship was cancelled/expired:
   - DO NOT silently pretend activation succeeded.
   - determine whether provider payment succeeded.
   - route the case through the existing reconciliation/refund/recovery logic.
9. Persist payment success and sponsorship activation atomically where the schema permits.
10. Commit.
11. Only then perform non-critical asynchronous work.

Do not allow a successful payment to produce a successful invoice while leaving the sponsorship in a cancelled state.

==================================================
REQUIRED FIX #5 — IDEMPOTENCY
==================================================

Payment finalization must be idempotent.

If the same PayPal webhook/capture/finalization is received twice:

- do not create duplicate sponsorships
- do not double-charge
- do not create duplicate invoices
- do not increment counters twice
- do not change an active sponsorship back to pending/cancelled
- safely return the already-finalized result

Use the existing payment/provider identifiers and database constraints where available.

==================================================
REQUIRED FIX #6 — SWEEP SAFETY
==================================================

Review sweepExpiredSponsorships() completely.

The sweep must:

- acquire the same advisory lock used by activation
- re-read the sponsorship state after acquiring the lock
- verify it is still pending
- verify it is genuinely expired
- check provider/payment state when a provider order exists
- cancel only when it is safe to release the reservation
- never cancel ACTIVE
- never overwrite a successful payment
- never delete payment history
- never destroy invoice records

If provider status is uncertain:

PRESERVE + RECONCILE.

Do not guess.
