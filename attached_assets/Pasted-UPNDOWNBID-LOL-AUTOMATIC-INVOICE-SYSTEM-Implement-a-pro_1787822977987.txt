UPNDOWNBID.LOL — AUTOMATIC INVOICE SYSTEM

Implement a professional automatic invoice system for ALL successful/confirmed payments.

IMPORTANT:
Do NOT replace, rewrite, or break the existing payment system.
Do NOT change payment amounts, bidding logic, campaign logic, ranking logic, or payment-provider integrations.
First inspect the existing payment architecture and reuse it.

==================================================
1. WHEN TO GENERATE AN INVOICE
==================================================

Generate an invoice ONLY after a payment is successfully confirmed.

Invoice must NOT be generated when:
- checkout is started
- payment is pending
- payment fails
- payment is cancelled
- payment requires reconciliation
- payment is refunded unless a separate refund/credit-note system is implemented

The payment record must be the source of truth.

Avoid duplicate invoices if the payment webhook/event is delivered more than once.

Each confirmed payment must have exactly one invoice unless the existing business rules explicitly require otherwise.

==================================================
2. PAYMENTS THAT REQUIRE INVOICES
==================================================

Generate invoices for all successful UpDownBid payment types, including:

- Claim / OWNER_BID
- Boost / COMMUNITY_BID
- Push Down / PENALTY
- Any other existing paid transaction type

Do NOT assume only one payment type exists.

Inspect the existing payment enum/types and support all successful paid transaction types.

==================================================
4. INVOICE NUMBER
==================================================

Create a unique sequential invoice number.

Example:

UPB-2026-000001
UPB-2026-000002
UPB-2026-000003

The invoice number must be generated server-side.

Never rely on the browser to generate invoice numbers.

Invoice numbers must remain unique even if two payments are confirmed at the same time.

==================================================

Add an invoices table if one does not already exist.

Add a unique constraint on:

invoice_number

Use the existing database conventions and ORM/migration system.

Do NOT manually modify production data.

==================================================
9. EMAIL FAILURE HANDLING
==================================================

A payment must NOT be marked failed just because invoice email delivery fails.

Payment confirmation and invoice generation are separate concerns.

Correct flow:

Payment confirmed
      ↓
Create invoice
      ↓
Generate PDF
      ↓
Attempt client email
      ↓
Attempt admin email

If email fails:

- Keep payment status = successful/confirmed
- Keep invoice status
- Record email delivery failure
- Allow retry
- Do not charge the customer again
- Do not create another invoice

==================================================
10. IDEMPOTENCY
==================================================

This is extremely important.

Payment providers can send the same webhook multiple times.

The system must prevent:

Payment received
→ Invoice 1

same webhook repeated
→ Invoice 2 ❌

Correct:

Payment received
→ Invoice 1

same webhook repeated
→ Existing Invoice 1 reused
→ No duplicate invoice
→ No duplicate emails unless explicitly retrying delivery

Use payment_id as an idempotency key.

13. REFUNDS
==================================================

Inspect the existing payment/refund functionality.

==================================================
14. RECONCILIATION SAFETY
==================================================

Payments with:

requires_reconciliation
pending
failed
cancelled

must NOT automatically receive a "PAID" invoice.

A payment that requires reconciliation must remain untouched until successfully confirmed.

This is especially important for the existing legacy payment records.

==================================================
17. SECURITY
==================================================

Never allow the client to:

- change invoice amount
- change invoice number
- change payment status
- generate a fake paid invoice
- download another client's invoice

Invoice data must be generated from the verified payment/database records.

All invoice downloads must verify ownership or admin authorization.

==================================================
18. EXISTING PAYMENTS
==================================================

Do NOT automatically generate invoices for old historical/test payments unless explicitly requested.

This implementation should apply to NEW confirmed payments.

Existing payments can remain unchanged.
